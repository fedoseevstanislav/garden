# Цикл проверки (review-loop)

**Язык:** ведите диалог на языке, на котором пишет участник (справочные файлы навыка написаны по-русски — это не требование к языку разговора; при ответах на другом языке переводите нужные формулировки на лету, суть таблиц не меняя).

Правило одно: **автор не проверяет свою работу**. Тот, кто написал текст или код, не видит в нём собственных дыр — он видит свой замысел. Проверять должна другая модель: лучше из другого семейства, но как минимум другая.

Этот навык НЕ строит. Сборка — обычная работа с агентом после подтверждённого мини-ТЗ. Навык включается, когда результат уже существует: вы вызываете проверяющего, чините только провалившееся и повторяете — цикл «проверка → правка».

## Шаг 0. Входные данные

Аргументы команды (все необязательные, в любом порядке): путь к мини-ТЗ (обычно `мини-тз.md`), путь к результату, число раундов. Результата ещё нет — остановитесь одной строкой: «сначала соберите, потом проверим». Раундов по умолчанию 3, допустимо 1–5; больше пяти не бывает — просят 10, скажите одной строкой, что потолок 5.

Ожидаемый формат мини-ТЗ — файл `мини-тз.md` из навыка `mini-tz`: критерии пронумерованы `C1…Cn` (каждый с тегами `проверяет: скрипт|судья|я` и `обязательный|качество`), запреты — `A1…An`. По этим же идентификаторам отчитывается проверяющий.

Если мини-ТЗ нет — остановитесь и одной строкой отправьте участника пройти `/mini-tz`: без критериев проверять нечего, а придуманные вами критерии — это снова автор, проверяющий сам себя.

## Шаг 1. Выбор проверяющего (выполнить до работы)

Проверяющий обязан быть **другой моделью**. Другое семейство — предпочтительно; другая модель того же семейства — допустимо. Та же модель — нет. Порядок проверки:

**Если вы в Claude Code:**
1. `command -v codex` — есть? Проверка идёт через `codex exec`: другое семейство, другая подписка, предпочтительный вариант.
2. Нет `codex` → подзадача (subagent) с **явно указанной другой моделью**: Opus → Sonnet, Sonnet → Opus. Свежий контекст, без истории вашей работы.

**Если вы в Codex:**
1. `command -v claude` — есть? → `claude -p --model <другая модель>`.
2. Нет `claude` → `codex exec -m <id, отличный от модели сессии>`. Модель сессии возьмите из контекста; не видна — спросите участника и назовите другую.

**Если другой модели не достать вообще:** скажите об этом прямо и остановитесь. Проверять той же моделью нельзя — это не проверка, а второй проход автора. Молча подменять проверяющего нельзя никогда.

Одной строкой скажите, кто проверяет: `Проверяющий: codex exec (gpt)` / `subagent Sonnet`.

## Шаг 2. Работа

Сделайте то, что просит мини-ТЗ. Обычная работа, без оглядки на проверку.

## Шаг 3. Проверка

1. Критерии с тегом `проверяет: скрипт` вы прогоняете **сами, до вызова проверяющего**: выполните названную команду (поиск, тест, линтер) и вставьте в запрос саму команду и её вывод. Проверяющий по такому критерию цитирует ваш вывод, а не перепроверяет его руками.
2. Соберите файл запроса: возьмите `references/reviewer-prompt.md` этого навыка, подставьте в него критерии из мини-ТЗ, пути к результату и вывод команд из пункта 1. Сохраните как `следы/review-запрос-<раунд>.md`.
3. Запустите проверяющего:

```bash
# вариант Claude Code → Codex, папка под git
codex exec -s read-only - < следы/review-запрос-1.md

# то же, если папка НЕ под git — добавьте флаг
codex exec -s read-only --skip-git-repo-check - < следы/review-запрос-1.md

# вариант Codex → Claude
claude -p --model sonnet --tools Read,Glob,Grep < следы/review-запрос-1.md
```

Общего сандбокса у двух CLI нет: у Codex права режет `-s read-only`, у Claude — список инструментов `--tools Read,Glob,Grep`. Смысл один: проверяющий читает и ничего не меняет. Флаг не принят вашей версией — посмотрите `claude -p --help` или `codex exec --help`.

4. Подзадача: тот же текст запроса — subagent'у с явной другой моделью.

**Проверяющий не правит текст и не предлагает формулировок.** Его рамка: «твоя работа — найти, где это НЕПРАВИЛЬНО, а не улучшить». Он только режет.

## Шаг 4. Вердикт

Проверяющий возвращает: первой строкой **ПРИНЯТО / ДОРАБОТАТЬ / ОТКЛОНИТЬ**, дальше по каждому `C1…Cn` и `A1…An` цитата-доказательство и **ПРОШЁЛ / НЕ ПРОШЁЛ / НЕ МОГУ ПРОВЕРИТЬ**, затем не больше 5 замечаний в форме «где — что нарушено — какой критерий (id)».

Правило приёмки одно: `ПРИНЯТО` — когда все `обязательный` критерии `ПРОШЁЛ` и не нарушен ни один запрет `A`. Критерии `качество` в вердикте отчитываются, но приёмку не блокируют.

Критерии с тегом `проверяет: я` проверяющий не оценивает: по ним он возвращает `НЕ МОГУ ПРОВЕРИТЬ` с пометкой «проверяет человек», а вы показываете их участнику отдельным списком «на вашу проверку». Поэтому такой критерий не может быть `обязательный` — если в мини-ТЗ встретилось `я · обязательный`, остановитесь и попросите участника либо сменить вид на `качество`, либо назвать, кто ещё может это проверить.

Покажите вердикт целиком, без пересказа.

## Шаг 5. Правки и следующий раунд

- Чините **только** пункты `НЕ ПРОШЁЛ`. Замечания без привязки к идентификатору — не чините, покажите их участнику отдельным списком в конце.
- `НЕ МОГУ ПРОВЕРИТЬ` с пометкой «проверяет человек» — не правка: несите участнику. Остальные — сигнал, что критерий непроверяем или проверяющему не хватило файла: дайте файл или скажите участнику переписать критерий.
- Раунд 2 и дальше: блок предыдущих замечаний идёт в запрос **после** основного задания, с пометкой, что читать его можно только после собственной оценки (двухфазный протокол в `references/reviewer-prompt.md`).

**Выход из цикла:**
- вердикт `ПРИНЯТО` → готово;
- достигнут лимит раундов (максимум пятый) → выведите оставшийся список `НЕ ПРОШЁЛ` и остановитесь. Работа не принята. Молчаливой приёмки не бывает.

## Шаг 6. След

После каждого раунда — одна строка в `следы/review-loop.md` (папку создайте, если её нет):

```
2026-08-23 | раунд 2 | codex exec (gpt-5) | ДОРАБОТАТЬ | НЕ ПРОШЁЛ: 2 (C2, A1)
```

## Запреты

- Не проверять свою работу самому и не пересказывать вердикт своими словами.
- Не чинить то, что не привязано к критерию.
- Не объявлять работу принятой без строки `ПРИНЯТО` от проверяющего.
- Не давать проверяющему право записи в файлы.Перед запуском **явно подтвердите с участником связку**: одной строкой назовите, кто будет проверять (инструмент и модель) и с каким усилием, и дождитесь «да». Модель и усилие подбирайте под задачу: короткий текст или список — лёгкая модель, обычное усилие; код, логика, многокритериальная приёмка — сильная модель, высокое усилие. Участник вправе назвать свою связку — она важнее вашего выбора
